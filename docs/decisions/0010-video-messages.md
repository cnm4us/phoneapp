# 0010 Video messages through the existing private media boundary

Status: accepted for synthetic implementation, 2026-11-19 UTC. [Plan 0014](../plans/0014-video-messages.md). Physical/native acceptance remains separate.

Extend the existing `audio_messages` table additively under migration 0006, preserving message/patient IDs and existing audio files. `media_kind` defaults to audio, with nullable verified video/poster metadata. New clients opt into `/messages/v2` for mixed history/create/grants; the legacy contract filters video before pagination and refuses video grants, preserving old audio clients. Patient/team access, sender-only unpublished drafts, stable send UUID/hash and session-bound short-lived media grants are retained. Private JPEG posters require their own grant operation and share the video's expiry and cleanup.

Pin SDK-compatible Expo Camera 57.0.6 and Video 57.0.5 alongside existing Audio 57.0.5. Native recordings use the camera module, browser uses runtime-tested MediaRecorder types. Native playback downloads to bounded app-private temporary files; browser uses authenticated fetch/Blob. No persistent player cache, photo-library save, background playback or PiP is enabled. Expo Video's config intentionally leaves existing background modes alone: setting its background/PiP flags false removes the audio background mode needed by native calling. Runtime player flags disable those message behaviors instead.

Video-with-sound is deliberate, foreground-only capture: choose camera first, Record, Stop, Preview/Re-record/Discard, Send. Preserve audio as a separate option. Call/background/logout/interruption releases message camera/audio and never resumes capture automatically. Version/anchor-guarded native patches subscribe camera/video modules to existing early native call signals; force Expo Audio/Camera/Video source builds through autolinking so patches are compiled. New EAS previews and physical CallKit/Telecom interruption tests are required; source/package inspection is not a phone test.

Normalize supported local inputs to H.264/AAC MP4 plus one JPEG poster, upright and aspect-preserving, at most 720p/30 and two minutes. Initial bounds: 64 MiB input, 32 MiB output, 256 KiB poster, 256 MiB video input per sender/day, 100 total messages/day, four total queued/active video jobs. Retain existing audio limits, seven-day media and 24h incomplete lifetimes, shared 1 GiB store/free-space floor, two uploads and one low-priority converter. Admission serializes reservations across concurrent uploads; output/temp space is reserved as well as input. Keep local format/protocol/codec and input dimension/rate limits. Each video subprocess is bounded to 300 CPU/wall seconds, 1 GiB address space and 32 MiB output. Video job lease is 660 seconds to cover conversion plus poster/probes; upload deadline ten minutes. Short-lived grants must be valid at request start; accepted streams retain bounded deadlines and recheck auth at completion. Individual JSON requests retain a ten-second deadline; nginx expands only the media route.

The first actual full-length synthetic 720p/30 conversion on this 2-vCPU EC2 took 34.69 seconds, produced 31,295,825 bytes and a 5,543-byte poster, with about 1 ms maximum Node timer delay in that sample. This supports continuing the bounded prototype; it does not establish simultaneous-call capacity, perceptual synchronization or physical-device compatibility. Record resource/call regression and cross-format evidence before final enablement.

Disabling the video flag blocks new video create/upload and preserves schema/history and retained published playback; workers drain accepted jobs with existing safeguards. Roll back using schema-compatible code/feature control, never by dropping history or restoring an old schema-blind binary. Revisit full-download playback for weak-link delay, processing isolation for load, and object storage/identity/retention for production; those remain separate work.

Native-format refinement, 2026-11-19: owner iPhone files have one additional opaque data/mebx track. Permit at most that single known extra video metadata stream, never decode/copy it, and verify output consists only of audio/video. Unknown extra tracks remain rejected. Synthetic three-track regression and recovery/public-history verification of the two existing uploads pass; this is a backend-only compatibility correction, not a new native dependency or migration.
